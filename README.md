# 院内患者管理支援ツール(ローカルAI版)

CSV/Excelではなく院内DBを想定した、患者情報・病棟ベッド管理と、ローカルLLMによる自然言語検索を組み合わせたポートフォリオ用サンプルアプリです。

> **重要**: 本アプリで使用している患者名・データはすべて架空のものです。実在の人物・医療機関とは一切関係ありません。
> また、AIによる**診断・治療方針の判断は行いません**。あくまで検索・要約による業務効率化の支援を目的としています。

---

## 目的・背景

医療機関向けの業務システム開発案件を想定して作成したポートフォリオです。特に以下の2点を重視しています。

1. **機密性の高い個人情報を扱う前提での設計**(ロールベース権限、変更履歴・操作ログの記録)
2. **AI/LLM活用と情報管理の両立**(患者情報を外部に送信しないローカルLLM構成、LLMに渡す前の仮名化処理)

---

## 主な機能

| 分類 | 内容 |
|---|---|
| 患者情報管理 | 登録・検索・編集、変更履歴の自動記録 |
| 病棟・ベッド管理 | 病棟/病室/ベッドマスタ、空床状況の一覧表示 |
| 入退院・転棟 | 入院/退院/転棟の処理と履歴管理(`admissions`テーブル) |
| 権限管理 | 医師/看護師/事務のロールベースでページ・機能を出し分け |
| 監査ログ | 閲覧・編集・入退院・AI問い合わせを含む全操作を記録(事務のみ閲覧可) |
| ユーザー管理 | アカウントの一覧・新規作成(事務のみ) |
| AI検索 | ローカルLLM(Ollama)による自然言語検索・要約 |

---

## 技術スタック

- **Streamlit**: UI(フロント・バックエンド一体)
- **SQLite**: DB(本番運用ではSQL Server等への移行を想定。テーブル設計はRDBMS非依存で作成)
- **Ollama**: ローカルLLM実行基盤(モデルは環境変数`OLLAMA_MODEL`で切替可能)
- **bcrypt**: パスワードハッシュ化
- **pandas**: 集計・一覧表示
- **fpdf2**: レポートPDF出力(過去のポートフォリオで確立した日本語組版ロジックを流用予定)

## セットアップ手順

### 1. リポジトリを取得し、仮想環境を作成

```bash
git clone <このリポジトリのURL>
cd hospital-ward-management-local-ai
python -m venv venv
venv\Scripts\activate   # Windowsの場合
```

### 2. 依存パッケージをインストール

```bash
pip install -r requirements.txt
```

### 3. Ollamaをインストールし、モデルを取得

[Ollama公式サイト](https://ollama.com/)からインストール後、以下でモデルを取得します。

```bash
ollama pull hf.co/elyza/Llama-3-ELYZA-JP-8B-GGUF:Q4_K_M
```

取得後、`ollama list`で表示されるモデル名を確認し、下記のように環境変数`OLLAMA_MODEL`に設定してください。デフォルト値は`elyza:8b`です。

```bash
# Windowsの場合(コマンドプロンプト)
set OLLAMA_MODEL=elyza:8b

# Windowsの場合(PowerShell)
$env:OLLAMA_MODEL="elyza:8b"
```

軽量なPCでは`qwen2.5:3b-instruct-q4_K_M`等への切り替えも可能です(同じく`OLLAMA_MODEL`で指定)。

#### モデル名を短い別名に変更したい場合(任意)

`hf.co/elyza/Llama-3-ELYZA-JP-8B-GGUF:Q4_K_M`のような長いモデル名は、`ollama cp`で短い別名(エイリアス)を付けることができます。実体は同じモデルなので、ディスク容量が二重にかかることはありません。

```bash
ollama cp hf.co/elyza/Llama-3-ELYZA-JP-8B-GGUF:Q4_K_M elyza:8b
```

実行後、`ollama list`を確認すると同じID(モデル実体)に対して2つの名前(`hf.co/...`と`elyza:8b`)が表示されます。これ以降は短い方の名前(`elyza:8b`)を環境変数`OLLAMA_MODEL`に設定して使えます。不要になった長い方の名前だけを削除したい場合は以下を実行してください(実体は`elyza:8b`側に残るため削除されません)。

```bash
ollama rm hf.co/elyza/Llama-3-ELYZA-JP-8B-GGUF:Q4_K_M
```

### 4. DBを初期化(ダミーデータ投入)

```bash
python init_db.py
```

### 5. アプリを起動

```bash
python -m streamlit run app.py
```

(`streamlit run app.py`ではなく`python -m streamlit run app.py`を使うのは、PATHの設定によって`streamlit`コマンドが認識されない環境があるためです)

## 設計上の工夫

### 1. 患者情報を仮名化してからLLMに渡す

`ai_search.py`では、患者の実名を`P001`のような仮名IDに変換したデータのみをローカルLLMに渡し、回答表示の直前に実名へ復元しています。ローカルLLMを使うこと自体が「外部に送信しない」という対策ですが、それに加えてプロンプトやログの中身にも実名を残さない設計にすることで、多層的な情報保護を意識しました。

### 2. 変更履歴(`patient_history`)と操作ログ(`audit_log`)の分離

前者は「データの値がどう変わったか」、後者は「誰がいつ何をしたか」という粒度の異なる記録を別テーブルに分けています。AIへの問い合わせ内容も`audit_log`に記録することで、「AIに何を尋ねたか」まで後から追跡できるようにしました。

### 3. 入退院・転棟を`admissions`テーブルの履歴として管理

患者マスタ(`patients`)とは別に、入退院の1回ごとの記録を`admissions`に保持する設計にしました。`discharged_at IS NULL`のレコードが「現在の入院状況」を表すため、同じ患者が過去に何度入院したかも追跡できます。

### 4. ロールベースの画面出し分け

サイドバーのページ自体をログインユーザーのロールによって出し分けています(監査ログ・ユーザー管理は事務のみ)。今回はシンプルな実装ですが、実案件では画面単位だけでなく操作単位での権限チェックまで踏み込む必要があると考えています。

## なぜクラウドにデプロイしていないか

本ツールは「患者情報等の機密データを外部に送信しない」ことを技術的な軸としています。クラウドにデプロイして常時稼働のデモを公開してしまうと、この設計思想と矛盾するため、あえてデプロイせずローカル実行のみとしています。動作の様子は下記のデモ動画/GIFでご確認いただけます。

## 制限事項

- 本アプリはポートフォリオ・技術検証用のサンプルであり、実際の医療機関での運用を想定した設計・検証(法令対応、可用性、バックアップ体制等)は行っていません。
- AI検索の回答精度はローカル小型LLMの性能に依存します。数値の解釈や複雑な集計を伴う質問では、誤った回答をする可能性があるため、実運用では出力の検証プロセスが必要です。
- 現時点では手術・検査予約、スタッフスケジュール管理などの機能は未実装です(スコープ外)。
